# JWT Rotation과 WebSocket 예외 격리를 왜 쓰는지 이해하기

용어가 어려워 보여도 결국 이유는 단순했음. "문제가 생겨도 피해를 작게 막으려고" 쓰는 거였음

## 1. JWT가 뭔지부터

JWT는 그냥 "로그인했다는 증명서"라고 생각하면 됨. 로그인하면 서버가 긴 문자열을 하나 줌. 그 다음부터는 요청할 때마다 이 문자열을 같이 보냄.

```
Authorization: Bearer eyJhbGci... (긴 토큰 문자열)
```

서버는 이 토큰만 보고 "아 로그인한 사람 맞네" 하고 통과시킴. DB를 안 뒤져봐도 돼서 빠름.

근데 여기서 약점이 보임. 서버가 토큰만 보고 믿어버리니까, 누가 내 토큰을 훔쳐서 들고 오면 서버는 그게 도둑인지 나인지 구분을 못 함. 토큰만 멀쩡하면 그냥 통과시킴.


## 2. 토큰을 왜 두 개로 나누는가

이 약점 때문에 토큰을 두 종류로 나눠서 씀.

- **Access Token**: 수명 짧음 (예: 30분). 실제 요청할 때 쓰는 토큰.
- **Refresh Token**: 수명 김 (예: 2주). Access가 만료되면 새로 받아오는 용도.

처음엔 "왜 굳이 두 개야?" 싶었는데 이유는 이랬음.

- Access를 짧게(30분) 만들면, 훔쳐가도 금방 만료돼서 피해가 작음.
- 근데 30분마다 다시 로그인하라고 하면 너무 짜증남.
- 그래서 수명 긴 Refresh로 자동으로 새 Access를 받아오게 함. 사용자는 로그인 끊긴 줄도 모름.

```
로그인       → Access(30분) + Refresh(2주) 받음
30분 뒤      → Refresh 보내서 새 Access 받음
             → 나는 아무것도 안 했는데 계속 로그인된 상태
```


## 3. Refresh Token이 털리면 왜 위험한가

Access는 30분이면 죽으니까 그나마 괜찮음. 문제는 Refresh임.

Refresh는 2주짜리임. 이게 털리면 도둑이 2주 동안 계속 새 Access를 받아갈 수 있음. 더 무서운 건, 나는 내 Refresh가 털린 줄도 모름. 나도 멀쩡히 잘 쓰고 있으니까.

그래서 나온 게 Rotation(회전)임.


## 4. JWT Rotation이 뭔가

한 줄로 말하면 이거임.

> Refresh를 한 번 쓸 때마다, 그 Refresh는 버리고 새 Refresh를 같이 줌. 즉 Refresh를 일회용으로 만듦.

Rotation을 안 쓰면 이런 식임:

```
Refresh(A) 사용 → 새 Access만 줌. A는 계속 살아있음
Refresh(A) 사용 → 또 새 Access. A는 아직도 살아있음
                 (A가 2주 내내 안 죽음 → 털리면 끝장)
```

Rotation을 쓰면 이렇게 바뀜:

```
Refresh(A) 사용 → 새 Access + 새 Refresh(B) 줌. A는 버림
Refresh(B) 사용 → 새 Access + 새 Refresh(C) 줌. B는 버림
                 (쓸 때마다 토큰이 바뀜. 한 번 쓴 건 바로 죽음)
```

마치 놀이공원에서 놀이기구 한 번 탈 때마다 티켓을 새 걸로 바꿔주는 느낌임. 쓴 티켓은 그 자리에서 못 쓰게 됨.


## 5. Rotation을 왜 쓰는가

여기가 핵심임. 단순히 토큰을 바꾸는 게 목적이 아니라 도둑을 잡으려고 쓰는 거였음.

상황을 보면 이해가 됨. 도둑이 내 Refresh(B)를 훔쳤다고 하자.

```
1. 나:   Refresh(B)로 갱신 → 서버가 Refresh(C)를 줌. B는 죽음.
         이제 나는 C를 들고 있음.

2. 도둑: 훔친 B로 갱신 시도
         → 서버: "B는 이미 쓰고 버린 토큰인데?"
         → 죽은 토큰이 다시 들어옴 = 뭔가 이상하다 = 도둑이다!
```

이미 버려진 토큰이 다시 들어오는 건 정상이면 절대 일어날 수 없는 일임. 정상 사용자는 항상 최신 토큰만 들고 있으니까.

그래서 서버는 "이 계정 토큰이 털렸구나" 판단하고, 그 사람 토큰을 전부 무효화해버림(강제 로그아웃). 그럼 도둑도 못 쓰고, 나도 다시 로그인하면서 비밀번호 바꿀 기회가 생김.

> 정리: Rotation을 쓰는 이유는, Refresh를 일회용으로 만들어서 "이미 쓴 토큰이 또 들어오면 도둑"이라고 알아챌 수 있기 때문임. 단순히 수명만 줄이는 게 아니라 도둑질 자체를 감지할 수 있는 게 포인트임.

> 참고로 이게 되려면 서버가 "지금 유효한 Refresh가 뭔지"를 어딘가(보통 Redis나 DB)에 기억하고 있어야 함. 그래서 Refresh만큼은 서버에 저장해두고 씀.


## 6. WebSocket은 뭐가 다른가

이제 두 번째 주제임. 예외 격리를 이해하려면 WebSocket이 일반 HTTP랑 뭐가 다른지부터 알아야 함.

평소 쓰는 REST API(HTTP)는 "요청 한 번 → 응답 한 번 → 연결 끝"임. 한 번 주고받으면 연결이 바로 끊김.

```
[나] --요청--> [서버]
[나] <--응답-- [서버]   (끝. 다음에 또 요청하면 새로 연결)
```

WebSocket은 한 번 연결하면 계속 연결돼 있음. 채팅이나 실시간 알림처럼, 서버가 먼저 나한테 말 거는 기능에 씀.

```
[나] <===== 계속 연결됨 =====> [서버]
   서로 수시로 메시지를 주고받음
```

"연결이 계속 살아있다"는 이 점이 예외 처리에서 큰 차이를 만듦.


## 7. 예외 하나가 왜 연결을 끊는가

HTTP에서는 요청 하나에서 에러가 나도 그 요청만 실패하고 끝남. 다른 요청은 멀쩡함. 어차피 요청마다 따로따로니까.

근데 WebSocket은 다름. 메시지 하나 처리하다 에러가 나면 연결 자체가 끊어질 수 있음.

채팅으로 예를 들면:

```
[1시간째 채팅 중]
   → 메시지 하나 처리하다 NullPointerException 터짐
   → 에러가 처리 안 되고 그대로 위로 올라감
   → 연결이 끊김 → 갑자기 채팅방에서 튕겨나감
```

메시지 딱 하나 잘못됐다고 채팅 전체가 끊기는 거임. 이게 문제임.


## 8. 예외 격리가 뭔가

해결책은 단순함.

> 메시지 처리하다 에러가 나도, 그 에러를 잡아서(try-catch 같은 느낌) 처리하고 연결은 안 끊기게 함. 즉 에러의 피해를 "그 메시지 하나"로만 막아둠.

격리를 안 하면:

```
메시지에서 에러 → 그대로 올라감 → 연결 끊김 → 튕김
```

격리를 하면:

```
메시지에서 에러 → 잡아서 처리 → "전송 실패" 메시지만 그 사람한테 보냄
                              → 연결은 그대로 → 계속 채팅 가능
```


## 9. 예외 격리를 왜 쓰는가

이유는 세 가지로 정리됨.

**1) 사용자가 안 튕김.** 메시지 하나 잘못 보냈다고 채팅방에서 쫓겨나면 너무 별로임. 격리하면 "전송 실패" 정도만 뜨고 대화는 계속됨.

**2) 다른 사람한테 안 번짐.** WebSocket은 여러 사람이 같은 서버를 같이 쓰는 경우가 많음. 한 사람 메시지 에러가 잘못하면 옆 사람한테까지 영향을 줄 수 있는데, 격리하면 이걸 막음.

**3) 서버 속사정이 안 새어나감.** 에러를 그냥 흘려보내면 서버 내부 에러 내용(스택 트레이스 같은 거)이 사용자한테 그대로 보일 수 있음. 격리하면서 "전송 실패했습니다" 같은 깔끔한 메시지만 보내줄 수 있음.

Spring에서는 `@MessageExceptionHandler`라는 걸로 이 격리를 함. 이름 그대로 "메시지 처리 중 에러를 잡아주는 곳"임.

```java
@Controller
public class ChatController {

    @MessageMapping("/chat.send")  // 여기로 메시지가 들어옴
    public void send(ChatMessage message) {
        chatService.save(message);            // 여기서 에러 날 수도 있음
        broadcaster.send(message.getRoom());
    }

    // 위에서 에러가 나면 여기로 잡혀 들어옴 → 연결은 안 끊김
    @MessageExceptionHandler(Exception.class)
    @SendToUser("/queue/errors")  // 그 사람한테만 에러 메시지 보냄
    public ErrorResponse handle(Exception e) {
        return new ErrorResponse("메시지 전송에 실패했습니다.");
    }
}
```

`@MessageExceptionHandler`가 에러를 여기서 잡아주니까, 에러가 위로 올라가서 연결을 끊는 일을 막아줌. 이게 "격리"임.


## 10. 두 개의 공통점

처음엔 JWT Rotation이랑 WebSocket 예외 격리가 완전 다른 얘기인 줄 알았는데, 공부하고 보니 결국 같은 생각이었음.

> 문제가 생겨도, 그 피해를 최대한 작은 범위로 가둔다.

- JWT Rotation: 토큰이 털려도 → 피해를 짧게 끊고 도둑을 잡음.
- WebSocket 예외 격리: 에러가 나도 → 메시지 하나만 실패시키고 연결은 살림.

둘 다 "터질 걸 막을 순 없어도, 터졌을 때 피해를 작게 만든다"는 같은 원리였음. 이걸 어려운 말로 장애 격리(Fault Isolation)라고 부른다고 함. 왜 쓰냐고 물으면 이 큰 그림까지 같이 말하면 될 듯함.
