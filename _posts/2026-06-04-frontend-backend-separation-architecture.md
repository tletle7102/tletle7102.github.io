# 프론트엔드/백엔드 분리 아키텍처를 왜 쓰는가

처음 스프링 배울 땐 화면(HTML)도 서버가 만들고 데이터도 서버가 주는 줄 알았음. 근데 요즘은 프론트랑 백엔드를 따로 나눠서 만든다고 해서, 왜 그러는지 정리함


## 1. 모놀리식이 뭔가

모놀리식(monolithic)은 "한 덩어리"라는 뜻임. 한 프로젝트 안에서 화면 그리는 일(HTML)과 데이터 처리(DB, 로직)를 다 같이 하는 구조임.

예전 스프링 + Thymeleaf 방식이 이거임.

```
사용자 요청
   → 스프링이 DB 조회
   → 스프링이 HTML을 완성해서
   → 완성된 화면을 통째로 보내줌
```

화면과 서버 로직이 한 코드 안에 섞여 있음.


## 2. 그래서 뭐가 불편한가

처음엔 한 덩어리가 편해 보임. 근데 커지면 불편해짐.

- 화면만 살짝 고쳐도 백엔드까지 같이 빌드/배포해야 함.
- 프론트 담당, 백엔드 담당이 같은 코드를 건드려서 자꾸 부딪힘.
- 무엇보다, 앱(iOS/Android)을 추가하려면 답이 없음. Thymeleaf가 만든 HTML은 브라우저용이라 앱이 못 씀.


## 3. 분리하면 어떻게 되는가

프론트엔드와 백엔드를 아예 다른 프로젝트로 나눔.

- **백엔드**: 화면은 안 만듦. 데이터(JSON)만 줌.
- **프론트엔드**: 그 JSON을 받아서 화면을 그림. (React 같은 거)

```
[프론트엔드(React)] --데이터 요청--> [백엔드(Spring)]
[프론트엔드(React)] <----JSON------- [백엔드(Spring)]
   ↑ 화면 그리기는 여기서                ↑ 데이터만 책임짐
```

서버는 "재료(데이터)"만 주고, 화면 만드는 건 프론트가 함. 식당으로 치면 주방(백엔드)은 음식만 만들고, 플레이팅(화면)은 홀(프론트)이 하는 느낌임.


## 4. 분리하는 이유 정리

- **따로 개발/배포 가능**: 화면만 고치면 프론트만 다시 배포하면 됨. 백엔드는 안 건드림.
- **여러 클라이언트 지원**: 백엔드가 JSON만 주니까 웹, iOS, 안드로이드가 같은 백엔드를 같이 쓸 수 있음.
- **역할 분리**: 프론트 담당과 백엔드 담당이 각자 코드를 따로 가짐.

> 핵심: 백엔드를 "화면 만드는 곳"에서 "데이터 주는 곳"으로 바꾸는 게 분리의 본질임. 그래서 화면이 여러 개여도(웹/앱) 백엔드 하나로 다 감당할 수 있게 됨.
