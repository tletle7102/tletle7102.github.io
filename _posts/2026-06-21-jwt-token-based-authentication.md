# JWT 토큰 기반 인증

로그인 유지를 세션으로만 하는 줄 알았는데, 요즘은 JWT 토큰을 많이 쓴다고 함. 특히 "웹이든 앱이든 똑같은 방식으로 인증된다"는 점이 핵심이라 정리함


## 1. 세션 방식의 한계

옛날 방식(세션)은 이렇게 동작함.

```
로그인 → 서버가 세션을 자기 메모리에 저장 → 브라우저엔 세션 ID만 줌
이후 요청 → 세션 ID 보냄 → 서버가 자기 메모리에서 찾아 확인
```

문제는 서버가 로그인 정보를 자기 안에 들고 있어야 한다는 거임. 서버가 여러 대면 정보 공유가 번거롭고, 무엇보다 세션은 브라우저 쿠키 기반이라 앱에서 다루기가 깔끔하지 않음.


## 2. JWT 방식

JWT는 **로그인 증명서를 토큰(긴 문자열)으로 만들어 클라이언트한테 줘버리는 방식**임.

```
로그인 → 서버가 JWT 토큰 발급 → 클라이언트가 그 토큰을 보관
이후 요청 → 토큰을 같이 보냄 → 서버는 토큰 서명만 확인하고 통과
```

서버는 로그인 정보를 따로 저장 안 함. 토큰 안에 "누구인지"가 들어 있고, 서명으로 위조 여부만 확인하면 됨.


## 3. 핵심: 인증을 헤더로 한다

JWT는 요청 헤더에 토큰을 실어 보냄. 형식이 정해져 있음.

```
Authorization: Bearer eyJhbGci... (토큰)
```

이게 왜 중요하냐면, **헤더는 클라이언트 종류를 안 가림**.

- 웹(React)도 이 헤더에 토큰을 실어 보냄.
- 아이폰 앱도 똑같이 이 헤더에 토큰을 실어 보냄.
- 안드로이드 앱도 똑같음.

쿠키는 브라우저 위주라 앱에서 다루기 번거로운데, `Authorization` 헤더는 어떤 클라이언트든 똑같이 붙일 수 있음.

```
[웹]    Authorization: Bearer ... ─┐
[iOS]   Authorization: Bearer ... ─┼─> [백엔드]  같은 방식으로 인증
[안드로이드] Authorization: Bearer ... ─┘
```


## 4. 그래서 분리 아키텍처랑 잘 맞는다

앞에서 "백엔드 하나를 여러 클라이언트가 공유한다"고 했는데, 인증도 그래야 함. JWT는 클라이언트가 뭐든 같은 헤더로 인증하니까, 백엔드 하나로 웹/앱 인증을 다 똑같이 처리할 수 있음. 그래서 프론트/백엔드 분리, 여러 클라이언트 구조에서 JWT를 많이 씀.


## 5. 정리

- 세션은 서버가 로그인 정보를 들고 있어야 하고 쿠키 기반이라 앱에 불편함.
- JWT는 로그인 증명서를 토큰으로 만들어 클라이언트가 보관, 서버는 서명만 검증.
- 인증을 `Authorization: Bearer` 헤더로 하므로 웹/iOS/안드로이드가 다 같은 방식.

> "클라이언트 종류와 무관하게 같은 헤더로 인증"되는 게 JWT가 분리 아키텍처와 잘 맞는 이유임.
